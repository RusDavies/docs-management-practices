# Repository Brief

## Purpose

This repository is a Git-backed Markdown documentation set for practical management guidance across levels, disciplines, and operating contexts.

It is intended to be reusable source material for:

- internal management guidance
- public/professional management writing
- personal-brand/employment-facing content
- team operating playbooks
- manager enablement material
- templates and checklists for management practice

The repository should behave like a living documentation product: navigable, reviewable, versioned, cross-linked, and maintained deliberately.

## Target Class

Target class: **Git-backed Markdown documentation repository**.

That means the repo should prioritize:

- clear landing-page navigation
- stable file names
- explicit document ownership and purpose
- cross-links between related docs
- review gates for sensitive/public content
- source, permissions, and originality tracking
- Git history for decisions and meaningful changes
- lightweight checks for broken links, orphaned docs, and formatting drift

## Primary Audiences

- Managers and leaders using the guidance directly
- Russ as author/editor/curator
- AI agents or human contributors maintaining the docs
- Potential public readers if selected content is published later
- Recruiters, employers, or professional contacts if material is used for brand positioning

## Scope

In scope:

- people, team, project, product, customer, operations, succession, risk, culture, and related management disciplines
- audience-level guidance by management altitude
- management templates and checklists
- public-writing and publication-risk guidance
- repository governance and maintenance rules

Out of scope by default:

- legal advice
- HR compliance manuals for a specific jurisdiction
- exhaustive academic management theory
- private/personally identifying workplace case studies
- confidential employer/customer content
- public publication of sensitive sections without explicit review

## Maintenance Model

Use branch-per-work-item Git workflow:

1. Start from clean `master`.
2. Create a descriptive branch.
3. Make a scoped documentation change.
4. Run the smallest meaningful verification gate.
5. Commit the branch work.
6. Merge back to `master` deliberately.
7. Push `master` to the private GitHub remote.
8. Update TODO/backlog and memory when meaningful.

## Quality Bar

A useful change should usually improve at least one of:

- navigability
- clarity
- management usefulness
- publication safety
- example quality
- template usability
- cross-linking
- reviewability
- maintenance resilience

If a change only adds words, it has not automatically added value. Markdown can also be landfill. Attractive landfill, but still landfill.
