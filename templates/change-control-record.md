# Change-Control Record

## Purpose

Record material changes to scope, schedule, budget, quality expectations, delivery method, governance gates, or risk posture. Change control should govern tradeoffs, not punish learning.

## Usage Notes

- Use for meaningful changes, not tiny execution details. Bureaucracy can reproduce without encouragement.
- Make the tradeoff explicit: if scope increases, what happens to schedule, budget, quality, risk, or capacity?
- For production changes, name the change lead, implementer, verifier, rollback authority, and support handoff owner. If one person wears multiple hats, say so deliberately.
- In agile work, use this for external commitments and material constraints; do not turn every backlog refinement into a courtroom drama.

## Example

A customer requests a new integration after a fixed launch date has been agreed. The record should show whether scope is swapped, launch moves, capacity increases, risk is accepted, or the request moves to a later phase.
